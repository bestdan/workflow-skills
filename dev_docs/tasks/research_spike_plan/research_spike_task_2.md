## Context

`init` is what makes the reference implementation's three per-repo config knobs
unnecessary: the skill **owns** the directory convention, the coverage-file
location, and the `### Q<n>.` heading convention, so they are fixed by `init`
rather than configured per repo (design §"What is repo-specific", final
paragraph).

Scaffolding is the one place the script legitimately creates files. Everywhere
else, creating a file to make a record resolve is explicitly forbidden (design
§"What the skill must **not** do").

## Task

Implement `init` in `scripts/research-spike.py`:

- `init <project>` creates `<root>/dev_docs/research/<project>/` with:
  - `PROJECT.md` — charter stub: what is being built, why the spike exists, and
    a tracks index (empty at init).
  - `decisions.md` — empty, with a one-line header explaining that it is
    **organizer-owned** and that track agents file `state: proposed` blocks in
    their own `questions.md` instead.
  - `LEDGER.md` — the generated roll-up, with the ledger markers in place and a
    header stating it is generated by `write-ledger` and never hand-edited.
- `init <project> --track <name>` creates `tracks/<name>/` with:
  - `questions.md` — carrying the stored-ledger markers at the top and a
    commented example of the `### Q<n>.` heading convention, so the convention
    is installed rather than documented;
  - `obligations/` (with a `.gitkeep`, since an empty dir does not survive git);
  - **no** `contracts/` — it is optional, and creating it eagerly would create
    an empty directory subject to the task-4 coverage rule.
- `init` on an existing project **fails** rather than overwriting; `--track` on
  an existing track likewise. Exit `1` with a message naming the existing path.
- `--track` may be passed on the initial `init` and repeatedly afterwards
  (`init <project> --track <name>` on an existing project adds the track and is
  the documented way to grow one).
- Every generated markdown file must be `dprint`-stable — generated content
  that the formatter rewrites causes the same endless fight as a generated
  ledger (see task 7). Assert this in the tests below, not just by eye.
- The freshly-initialized tree must **pass `validate` clean** (exit 0). An
  `init` that produces a tree failing its own gate is the worst possible first
  impression; wire the assertion in tests now even though most rules land in
  tasks 3–5, and keep it passing as those land.

## Acceptance Criteria

**Code-enforced:**

- New fixtures in `scripts/test-research-spike.sh`:
  - `init foo` creates the four paths above and exits 0;
  - `init foo` twice fails with a message naming the existing project;
  - `init foo --track bar` creates `questions.md` with ledger markers and
    `obligations/.gitkeep`, and does **not** create `contracts/`;
  - a second `--track baz` on the same project succeeds and leaves `bar`
    untouched;
  - `validate` on the freshly-initialized tree exits `0`;
  - `dprint fmt` over a copy of the generated files produces **no diff**
    (skip with a clear message if `dprint` is not on `PATH`, so the harness
    stays runnable on a bare machine).
- `bash scripts/check.sh` green.

**User-run:**

- `python3 scripts/research-spike.py --root /tmp/rs init demo --track account`
  produces a tree that reads as a usable starting point, not a stub dump —
  open `PROJECT.md` and `questions.md` and confirm a newcomer could file a
  question without reading the design doc.
