# Now modes — rank the fleet Now by the kind of session the owner is in

Now (`fleet_now.py`) ranks one list by one score. On 2026-10-26 that list was
ten `auto:human-review-needed` issues, oldest first: nothing sat in the higher
categories, 24 issues tied at the score ceiling (category 3 + `prio:1` 0.6 +
age capped at 0.5), and the tie went to the longest wait. The ranking was
correct by its own rules and wrong for the owner, who had sat down to ship,
not to triage a backlog.

The owner's diagnosis: there is no single right order. Which item comes next
depends on the kind of session they are about to have, and on a personal
fleet, with no teammates blocking, prioritising is self-management. So Now
gets **modes**, picked by the owner, each answering a different question.

## Goals

- In-flight work outranks backlog by default.
- The owner picks a mode with one button at the top of Now that cycles through
  them. The modes apply to every instance (work or personal). The
  instance type is unrelated to the mode.
- Each mode has its own ordering. The modes are not one score with different weights.
- Every card still says why it is there (its `why` line) in terms of the active mode.

## Non-goals and anti-goals

- **No inferred mode.** The tool never guesses the mode from time of day or
  activity. (Newport's deep/shallow split argues for choosing the block
  deliberately.)
- **No setup ritual.** The removed Focus feature (#1182) asked the owner to
  hand-pick items, and went unused. A mode is one click and zero curation.
- No calendar or time-blocking. No model call at runtime (the existing
  rule).
- Not a new tab. Modes re-rank Now. Needs you and the other tabs are
  unchanged.

## Grounding

Each mode borrows from one line of research:

| Idea                                                                                       | Source                                     | Used in                           |
| ------------------------------------------------------------------------------------------ | ------------------------------------------ | --------------------------------- |
| Stop starting, start finishing: delay lives in wait states, so finish in-flight work first | Kanban WIP limits                          | Ship                              |
| An unfinished task degrades performance on the next one (attention residue)                | Leroy 2009, _OBHDP_ 109(2)                 | Ship (close-outs first)           |
| Cost of delay ÷ duration (CD3/WSJF)                                                        | Reinertsen                                 | Little tasks                      |
| Small, visible progress drives motivation more than anything else                          | Amabile & Kramer, _The Progress Principle_ | Little tasks (closed-today count) |
| Deep work is a separate, protected block with a WIP of one                                 | Newport, _Deep Work_                       | Deep work                         |

With agents doing the implementation, the owner's scarce resource is
decisions. Now is a decision queue, and deep mode puts the decisions that
unblock the most work at the top.

## The four modes

| Mode               | Question                          | Shows                                                                      | Limit |
| ------------------ | --------------------------------- | -------------------------------------------------------------------------- | ----- |
| **Ship** (default) | What is closest to done?          | sessions that asked → close-outs → ready to merge → review queue → started | 10    |
| **Little**         | What can I knock out fast?        | small items, smallest first                                                | 10    |
| **Deep**           | Which decision unblocks the most? | design and blocked questions, by what they unblock                         | 3     |
| **Tidy**           | What is rotting?                  | the backlog, oldest first                                                  | 10    |

The button cycles Ship → Little → Deep → Tidy → Ship and shows the current
mode's name.

### Ship

Today's categories, reordered so in-flight work leads, plus one new category.

1. `asked`: a session waiting on a prompt or a question. The owner listed
   close-outs first. Putting a blocked agent above them is the designer's
   call, because it is the one item whose wait stalls work already in
   progress.
2. **`close_out` (new).** Something finished that needs the owner to close
   it:
   - a finished session, from a close-out collector of its own. It has no
     `since_looked` window, unlike `needs.finished()`. A session enters only
     on evidence that its work is finished: its PR merged, its branch landed,
     or the session ended. A turn that merely ended is not enough, because
     `fleet_views.finished_sessions` returns every idle session;
   - a workstream in the `complete` lane (`workstreams._base_lane`): every
     issue done, no open PR, so close or archive its milestone.
3. Ready to merge: `quick_win` (bot PR, CI green), and the owner's PR that is
   approved with CI green. Today that PR is `own_pr`, ranked last. It
   moves up into this tier.
4. `review_queue`.
5. `started`.
6. Everything else, in today's category order.

`prio` and `age` still order items within a tier.

### Little

Only items that pass a **small** test, ordered by a size bucket, then `prio`,
then the longer wait. The buckets, smallest first: a bot PR, a docs-only PR,
an `est:1` issue, a PR of at most 3 files and 50 lines, an `est:2` issue.

- **PRs:** small when any of these hold:
  - a bot author (`author_is_bot`, which covers Dependabot);
  - docs-only, where every changed path is `*.md` or under `docs/` or
    `dev_docs/`;
  - at most 3 files and 50 changed lines.

  This needs `changedFiles`, `additions`, `deletions` and
  `files(first: N) { nodes { path } }` on both PR queries:
  `github_fleet.REVIEW_QUERY`, and `github_gh.SEARCH_QUERY`, which fills
  the `prs` table. They are stored in the row's existing `raw_json`, with no
  new columns. A PR with `changedFiles` greater than N is not docs-only,
  because its path list is incomplete.
- **Issues:** small when labelled `est:1` or `est:2`. An unsized issue is not
  small: unknown is not little.
- **Nightly review fixes:** the owner named these as routine. Nothing found
  so far marks them. Until one is found they qualify only through the PR
  size test.

Header: "closed today: N", counting PRs merged and issues closed since local
midnight, by anyone, across the `github.orgs` repos. It comes from its own
search per sync (see "Calls settled after review"). It does not come from
`CLOSED_QUERY`, which covers only the owner's PRs, or from the issue mirror,
which drops closed issues.

### Deep

Candidates: the questions that need thinking, not doing:

- proposed designs (`workstreams.mirrored_designs`, the `design` lane);
- issues at `status:1_needs_refinement`;
- issues that block other issues;
- `est:8` and larger issues that are `ready`. These are the big, chunky ones.

Order: the number of open issues each item blocks, highest first, then `prio`,
then size (largest first). Only 3 are shown, as a WIP limit of one with two
alternates.

"Blocks" comes from GitHub's native issue dependencies. **Check before
building** that the GraphQL `Issue` node exposes them (expected:
`blocking { totalCount }`) and that the owner's repos use them;
run one GraphQL query to settle it. The fallback is what `/reoptimize-tasks`
does (`commands/handlers/assets/gh-issue-graph.py`): a REST
`dependencies/blocked_by` read per issue, inverted into a blocks count. That
costs one call per open issue per sync, so prefer the GraphQL field if it
exists. If neither is affordable, deep mode ships without the blocks term and
orders by `prio` then size.

### Tidy

`human_issue`, `status:0_untriaged` and `status:1_needs_refinement` issues,
and stale own PRs, **oldest first**. The card
action is "close, supersede, or decide". This is the one mode where age is
the point.

## Mechanics

- **Selection.** The button POSTs the next mode, which is saved to the
  overlay (one row), then redirects to `/now`. A reload or a phone visit
  keeps it, and `export` and `import` carry it. A GET
  `?mode=ship|little|deep|tidy` shows that mode once and saves nothing. With
  no saved row the mode is Ship.
- **CLI.** `dashboard.py view now --mode <m>`, for agents and tests.
- **Why lines** name the mode's terms, for example `little · PR, 2 files, +14/−3`
  or `deep · blocks 4 issues · prio:1`.
- **"Why not now" answers** record the active mode in their snapshot, so
  `tune` can later propose weights per mode. Per-mode `tune` is out of scope
  here.
- **Config.** Ship keeps the `[score.fleet]` weights and adds `close_out` and
  `own_approved`, each with a default in `config.DEFAULTS["score"]["fleet"]`.
  The thresholds for Little (files, lines) and Deep (the limit) are module
  constants for now. Promote them to config only when the owner wants to tune
  them.
- Pins, ignores, snoozes and the include filter apply in every mode, as
  today.

### What closing out means

To the owner, closing out a finished session is a sequence:

1. merge its PR;
2. close its task;
3. leave the worktree for `main`, remove the worktree, and refresh `main`;
4. clear or end the Claude session.

So a `close_out` card shows that sequence as a **checklist**. Each step is
ticked from evidence the dashboard already mirrors, not from a click:

- **PR merged:** the PR's state (`CLOSED_QUERY`, `merged`).
- **Task closed:** the PR's closing issue is closed. The link is session →
  PR by (repo, head branch) → `closingIssuesReferences`. `CLOSED_QUERY`
  gains `closingIssuesReferences(first: 10) { nodes { number state
  repository { nameWithOwner } } }`, and the step ticks from that issue's
  own `state`. Absence from the open-issue mirror is not evidence. A PR with
  no closing issue gives no evidence for this step.
- **Worktree removed:** the host has reported a snapshot newer than the
  session's last event, and that snapshot lists no worktree at the session's
  cwd. A host with no such snapshot gives no evidence, and neither does a
  cwd outside the repos the snapshot scans (`snapshot.find_repos`).
- **Session ended:** the session row's `ended`.

A complete workstream has one step of its own instead: **milestone closed**,
ticked when the workstream leaves the `complete` lane because its milestone
was closed or archived. The session steps do not apply to it.

The card leaves Ship when every step it has evidence for is ticked. A step
with no evidence, such as a session with no PR, is skipped, not counted as
open. The dashboard stays read-only. The card's action is to resume the
session, by its Remote Control link or `claude --resume`, with the remaining
steps as the prompt, so the session finishes its own close-out. Snooze and
ignore remain the escape hatch.

## Calls settled after review

Recorded as the designer's calls; the owner can overturn any of them.

- **Candidate sets.** Ship ranks today's `fleet_now.candidates()` set plus
  close-outs. Little, Deep and Tidy each have their own collector over the
  issue mirror and the `prs` table, not a filter over `candidates()`.
  - **Little** excludes draft PRs and PRs whose CI is failing or pending. It
    takes `est:1` and `est:2` issues at any status except `status:3_started`.
  - **Tidy** takes `human_issue`, `status:0_untriaged` and
    `status:1_needs_refinement` issues, plus stale own PRs. A stale own PR is
    one open longer than Stale's `OPEN_ITEM_DAYS` (14), drafts and pending CI
    included.
- **Ship's order is fixed tiers in code.** The tier comes first, and the
  `[score.fleet]` weights order items within a tier. An approved own PR is
  in the ready-to-merge tier only with CI green. With CI pending it stays in
  the bottom tier. `FLEET_CATEGORIES` gains `close_out` and `own_approved`.
  `tune` still proposes weights, and they now act within a tier.
- **Close-out window and cap.** A close-out stays while its checklist has an
  unticked step, for up to `CLOSED_WINDOW_DAYS` (14) after the session's last
  event. That is as long as the dashboard can see a merged PR, and the same
  bound Needs you's Finished group uses when no visit is recorded. It leaves
  when the checklist is complete or the window passes, whichever comes first. At most 3 show on
  Ship, oldest first. A complete workstream gets an overlay item
  key (`workstreams`, its id), so the ordinary snooze and ignore apply to it.
- **Pins** show in every mode, ahead of the list, as today. Deep's limit of 3
  counts only items that are not pinned.
- **Persistence.** The button is a POST that saves the mode to the overlay
  and redirects. A GET `?mode=` is a one-off view and saves nothing, which
  keeps the rule that a page load records no state. `view now` with no
  `--mode` reads the saved mode, so an agent sees what the owner sees. Tests
  pass `--mode`.
- **Tidy** shows only its own collector's kinds, strictly oldest first, with
  no score. The limit is 10, with "N more" below.
- **"Closed today"** comes from one search per sync over the `github.orgs`
  repos: PRs merged and issues closed since local midnight, by anyone. This
  counts the fleet's output, not the owner's clicks. The open-issue mirror
  cannot supply it, because it drops closed issues.

## Left to the builder

- Where the button sits in the header, and how it looks.
- Whether each mode is a function in `fleet_now.py` or its own small module.
- The `close_out` weight value. Its tier is fixed in code, after `asked`, so
  the weight orders items only within that tier.
- The overlay migration shape for the mode row. Carrying it in `export`
  bumps `EXPORT_VERSION` to 7, and an import of version 6 or earlier reads
  the mode as absent (Ship).
